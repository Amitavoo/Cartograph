# **Phase 12 — Repository AI Agent**

**Goal.** Transform Cardograph from a static repository analysis application into an interactive AI research agent. Users should be able to ask natural-language questions about their analyzed repositories and watch the agent retrieve, navigate, and reason over repository data using dedicated tools. The agent should provide answers grounded in actual analysis data rather than relying on assumptions or generating unsupported explanations.

## **Build**

- **Agent tools.** Equip the AI agent with six dedicated tools to interact with repository analysis data:
  - **Analysis summary.** Retrieve the complete summary of the repository analysis, including its key findings and structural overview.
  - **File search.** Search for files using path segments or partial path matches.
  - **Role-based file listing.** Retrieve files filtered by their assigned roles, such as services, controllers, modules, or components.
  - **Neighbor lookup.** Retrieve the neighboring files and direct relationships associated with a specific file.
  - **Transitive traversal.** Explore dependency chains and transitive relationships to understand how changes to a file may affect other parts of the repository (blast radius analysis).
  - **Route table access.** Retrieve the analyzed application's route table to understand available endpoints and their associated files.
- **HTTP tool integration.** Implement the six agent tools as wrappers around the application's existing read-only analysis endpoints. Tools that perform dependency traversal must accept a starting file and traversal direction, allowing the agent to explore upstream or downstream relationships. Use HTTP clients to communicate with these endpoints rather than accessing the database directly from the agent.
- **Agent orchestration.** Configure the agent to select and invoke the appropriate tools based on the user's question. It should be capable of making multiple sequential tool calls when a question requires information from different parts of the repository. The final response must be grounded in the information returned by those tools.
- **Short-lived authentication credentials.** Implement a secure mechanism for generating short-lived signed credentials that associate an agent session with a specific analysis and organization. These credentials must be validated by the read-only API before allowing access to analysis data.
- **Organization-level isolation.** Ensure that every tool invocation is restricted to the organization associated with the authenticated session. The agent must never be able to retrieve analysis data belonging to another organization, even if it attempts to manipulate analysis identifiers or request parameters.
- **Ask interface.** Update the existing right-hand application pane to introduce an **Ask** tab alongside the existing interface. This tab provides the conversational interface through which users can ask questions about the currently analyzed repository.
- **Streaming tool execution.** Stream the agent's execution process to the frontend in real time. Users should be able to see:
  - The agent's reasoning status and current activity.
  - Which tool is being invoked.
  - The arguments or relevant input associated with the tool call.
  - The tool execution status and returned results.
  - The final answer generated after the required tool calls are completed.
- **Conversation context.** Maintain relevant conversation history so that users can ask follow-up questions without repeatedly specifying the same files, dependencies, or repository context. All conversation context must remain scoped to the active organization and analysis.

## **Constraints**

- **The agent must use tools, not guess.** Repository-specific questions must be answered using the six available tools. If the required information cannot be retrieved, the agent should explicitly communicate that limitation instead of inventing repository details.
- **Read-only access.** All six tools must interact with existing read-only analysis endpoints. The agent must not modify repository data, analysis results, or database records.
- **No direct database access.** The agent must retrieve information through HTTP clients and the application's existing API layer. Do not introduce a separate database connection for the agent.
- **Short-lived credentials only.** Never expose permanent service credentials, database secrets, or long-lived API keys to the agent or browser. Signed credentials must expire and be scoped to the intended analysis and organization.
- **Tenant isolation is mandatory.** Organization identity must be validated server-side. Never trust organization IDs, analysis IDs, or authorization claims supplied directly by the frontend or generated by the agent.
- **Tool boundaries must be enforced.** The agent can only access information exposed through its six registered tools. It must not execute arbitrary SQL, shell commands, filesystem operations, or unrestricted HTTP requests.
- **Streaming must reflect actual execution.** Tool calls, results, and execution states displayed in the Ask interface must correspond to real agent events. Do not simulate tool execution or display fabricated results.
- **Graceful failure handling.** If a tool fails, times out, or returns incomplete information, the agent should handle the failure gracefully and communicate what information could not be retrieved.
- **Analysis scoping.** Every conversation and tool execution must operate against the currently selected analysis. Switching analyses must not accidentally reuse credentials or repository context from the previous analysis.
- **Preserve the existing application.** Integrate the agent into the existing application shell and right-hand pane without disrupting existing analysis, navigation, or explanation functionality.

## **Acceptance check**

1. Open an analyzed repository and ask the agent for an overall repository summary. Confirm that it invokes the analysis summary tool and generates an answer using the returned data.
2. Ask the agent to find files containing a specific path segment. Confirm that it invokes the file search tool and returns matching files.
3. Ask which files belong to a particular role, such as services or controllers. Confirm that the role-based listing tool returns the appropriate files.
4. Select a file and ask which files are directly connected to it. Confirm that the neighbor lookup tool retrieves its relationships.
5. Ask the agent to explore the downstream dependencies of a specific file. Confirm that it performs a transitive traversal using the correct starting file and direction.
6. Ask which API routes are defined in the repository. Confirm that the agent accesses the route table and generates its response from the retrieved information.
7. Ask a question requiring multiple tools. Confirm that the agent can invoke multiple tools sequentially and combine their results into a coherent answer.
8. Inspect the Ask interface while a query is running. Confirm that tool calls, execution states, and returned results stream to the frontend in real time.
9. Attempt to access an analysis belonging to another organization using a modified analysis identifier. Confirm that the API rejects the request.
10. Allow a signed credential to expire and attempt another tool invocation. Confirm that the request is rejected and that the application handles the failure appropriately.
11. Switch between two analyzed repositories and ask similar questions. Confirm that each response uses the currently selected analysis and does not leak context from the previous one.
12. Ask a question that cannot be answered using the available repository data. Confirm that the agent admits the limitation instead of fabricating an answer.
13. Verify that all six tools operate exclusively through the existing read-only HTTP endpoints and cannot modify analysis data.
